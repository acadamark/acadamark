# Enscribe — Status

A capability checklist: what enscribe can do today, and what is planned
but not yet built. Checked items work and are tested; unchecked items are
intended but not started.

This file records **state, not history**. It is not a changelog — the
commit log is the changelog (`git log`). It is not an explanation — for
*why* the project exists read `README.md` and `DESIGN.md`; for the
architecture, `notes/specs/`. Open work is tracked in
[GitHub Issues](https://github.com/enscribejs/enscribe/issues); the release
sequence lives in `ROADMAP.md`. No counts (test totals, fixture totals)
appear here — a number is the fastest thing to go stale; run
`npm run verify` in `packages/enscribe` for the live test
status.

Legend: `[x]` works and is tested · `[ ]` planned, not started.

## Authoring — what a `.emd` document can express

- [x] Three authoring registers: canonical tags, sigil shorthands, markdown idioms
- [x] Tagged shorthand — `<tag #id .class attr=value +flag -flag | content>`. A **bare** attribute name that is a *known* boolean (an element's vocab boolean, or a boolean `<config>` kwarg) also means `true` — `<config toc>` ≡ `<config toc=true>`, `<section unlisted>` ≡ `<section +unlisted>` ([#219](https://github.com/enscribejs/enscribe/issues/219)) — the canonical HTML / eHTML spelling; a bare *unknown* name stays unrecognized (no phantom boolean), and bare resolves only for boolean kwargs (a valued kwarg like `toc-depth` still needs `=value`). Promoted in the shared gate, so static and live agree
- [x] Sigil tags — sections `<# #>`, inline/display math `<$ $>` `<$$ $$>`, code `` <` `> `` `` <``` ```> ``
- [x] Same-line long form — `<b>bold</b>` and `<tag>…</tag>` for every vocabulary tag
- [x] Self-closing form `<tag />`
- [x] Implicit section closing (a peer-level tag ends the previous)
- [x] Multi-line tag content; escape rules (`\<`, `\|`, `\\`, `&gt;`)
- [x] Nested tags inside named-tag content (recursive content parsing)
- [x] Bare markdown forms normalized to canonical nodes (`$x$`, GFM tables, emphasis/strong, strikethrough, inline code, links, headings)
- [x] Sections — three-level named ladder (`section` / `sub-section` / `sub-sub-section`)
- [x] Section numbering — opt-in via `<config number-sections />`, **default OFF for every document type** (#246/core — the previous on-for-books default was dropped; an unnumbered baseline is cleaner and the chapter rail orders a book without numbers); build-time hierarchical numbers (`3.1.2`) as real content, chapter-prefixed in books, with chapter (arabic) and appendix (alpha) book-part headings numbered; cross-refs render the number ("section 3.1.2", "chapter 1", "appendix A") and JATS carries `<sec><label>` / `<book-part-meta>…<label>`. **When a heading is unnumbered, a `<ref>` to it shows the heading's TITLE** ("see *Methods*") — sections and book-parts register their title for the fallback, so a cross-ref to an unnumbered chapter resolves to its title, not a ref-error. Separate-pages chapter **URLs are number-free** (the slug stem is decoupled from the chapter number), so a chapter's URL is stable whether or not numbering is on. Float numbering (figures/tables/equations) is independent and stays on. **`number-depth`** bounds the deepest numbered level ([#218](https://github.com/enscribejs/enscribe/issues/218); default all, **independent of `toc-depth`**), and **`<section +unnumbered>`** (a new sectioning boolean, sibling of `+unlisted`) puts a heading outside the sequence — no number and the counter does not advance, so the next numbered heading continues unbroken (the `\section*` / Quarto `.unnumbered` behavior). The stamp is in the shared `runSync`, so static and live number identically; numbered headings show their numbers in the config-driven contents listing (the un-glue path)
- [x] Appendices — `<appendix>`, one authoring element with two projections by `<meta type>` (#100): a **book** appendix → `<book-part book-part-type="appendix">` in `<book-back>` (BITS); an **article** appendix → JATS `<app>` collected in one `<app-group>` in `<back>`. Same authoring surface, title/id, render, and #57 appendix lettering (`A`, `A.1`, "Appendix A" cross-references) across both
- [x] Figures and images, with captions
- [x] Tables — the `<table>` host with CSV, TSV, JSON, YAML, and Markdown format words (`<csv>` / `<tsv>` kept as gate shorthands → `<table csv>` / `<table tsv>`)
- [x] Opt-in markup in data-table cells — data-format cells are literal by default; `+parse-text` / `parse-columns="…"` / `-parse-text` (and a doc-wide `<config parse-data-tables>`) opt cells into Enscribe inline markup (links, emphasis, cross-refs, cites, inline code/math), parsed in HTML and JATS both, with the stored data payload left literal
- [x] Inline and display math (KaTeX); numbered equations
- [x] Notes — one note type, three positions (foot / end / margin), numbering independent of position (#333). A document-level **margin render mode** (#33) `note-position=margin` (option or `<config>`) relocates every numbered note into a margin column beside its marker; a per-note `<note position=margin>` places a single note in the same margin. Below the breakpoint the margin copy hides and the bottom footnote list shows. JATS: position drives the element — a footnote → `<fn>`, a margin note → `<boxed-text content-type="marginnote">` — and both round-trip
- [x] Citations and bibliography — citation-js, the `<library>` storage host (`<library bibtex | …>` format word), inline BibTeX / CSL-JSON, CSL styles, and external sources via `<library src=…>` (#133): a filesystem path or http(s)/reachable URL, loaded at build (CLI) and on render in the browser (`renderAsync`, async fetch); multiple inline/`src` libraries merge with deterministic key-collision flagging; a failed load renders a visible error (always-renders). The old `<bibliography source=…>` form is retired
- [x] Cross-references to figures, equations, tables, sections, code blocks, theorems
- [x] Theorem family — `<theorem>`, `<lemma>`, `<definition>`, `<proof>`, … (shared / own / unnumbered counters)
- [x] Frameable boxed prose — `<aside>` joins `<frame>` with an optional title, caption, and border (on by default); a numbered `<aside>` gets its own "Box" counter, and `<aside type=…>` carries the callout taxonomy (the admonition types — note / info / tip / warning / caution — are styled per-type by the default theme) + `<boxed-text>` export
- [x] Frameable border looks — `border=<name>` selects a named look (`accent` / `thick` / `dashed` / `subtle` in the default theme) on the frameable border surface; the document names the look, the theme defines it (`frameable-border-<name>` modifier class)
- [x] External DSLs — the `<diagram>` host (Mermaid, ABC engines as format words); legacy `<mermaid>` / `<abc>` kept as gate shorthands
- [x] Host format-word validation — a format-word host (`<table>` / `<diagram>` / `<library>`) carrying a format outside its accept-set (e.g. `<table xml>`, `<diagram mermaidx>`) gets a located, non-fatal diagnostic at the gate and still renders
- [x] Inline SVG — the `<svg>` frameable element (bare inline, or captioned / numbered → wrapped in `<figure>`); the canonical home for framed inline SVG (no `<fig svg>`)
- [x] Minipage — `<minipage>` (#115), a sealed frameable: outwardly an ordinary frameable in a `<figure>` (its own "Minipage N" series, `mp` ref-prefix, border on by default, numbered opt-in), inwardly a self-contained sub-document processed in its own pipeline run with its own registry. Private internal numbering, box-local (LaTeX bottom-of-box) footnotes, inbound refs to the body forbidden, one-way read-through outbound refs (body → document resolve; child labels never merge up), nested minipages, and a no-external (`@src` / `<data>`) guard
- [x] Links with a positional URL (`<a url | text>`)
- [x] Book structure — chapters, parts, front/back matter
- [x] Lists — the `<list>` / `<list ordered>` construct with **open item markers**: `<li>` (canonical), the `<->` / `<*>` sigils (strict-safe), and the `-` / `*` markdown idiom. An item's content is the flow that follows its marker (peer-closed by the next marker or `</list>`), so items hold multiple paragraphs and nested `<list>`s with no indentation. `marker=` (→ CSS `list-style-type`), `start`, and `reversed` are supported. Lowers to standard `<ul>` / `<ol>` + `<li>`, inheriting the HTML render and the JATS `<list>` mapping.
- [x] Strict mode — the strictness register switch (#36): `<config strict-mode=off|sigil|canonical>` (or the `strictMode` render option, which wins). Each value names the loosest register still interpreted. `sigil` turns the markdown register off — `*`, `#`, `-`, `>`, `` ` ``, `$…$` pass through literal everywhere, including inside tag pipe bodies, with no escaping — while canonical tags and sigils stay live, and would-be-markdown text is flagged. `canonical` turns markdown **and** sigils off (`<# #>` / `<$ $>` / `<->` / `<*>` literal too), leaving only the canonical named-tag register — the canonical `<li>` and the `^{}`/`_{}` shortcuts stay live — and flags would-be-markdown **and** would-be-sigil text. The flag CSS is injected only for a non-`off` rung. `off` (default) is the unchanged single parse → byte-identical. Native inferences (blank-line→paragraph, section nesting) stay on in all states; eHTML / JATS are unaffected, and `enscribe lift` honors the mode so `sigil`/`canonical` documents round-trip losslessly. Mechanism: parse off, then re-parse with the register(s) disabled (markdown via micromark `disable`; sigils via the sigil-less `enscribeSyntax` variant)
- [ ] `<html-passthrough>` — needs a spec first
- [x] Multi-file source, article level — a master document (`<meta>` / structure / `<data>` / `<config>`) assembles `<section src>` child files into one article (design of record: `notes/specs/master-document.md`; epic [#190](https://github.com/enscribejs/enscribe/issues/190)). `enscribe build` parses the master → loads + parses each child → assembles in document order → renders as one article, with **numbering and cross-references resolved across files**: figures and sections number continuously through the assembled document, and a `<ref>` resolves to its target wherever it lives across the children (an unresolved ref renders a visible marker, not a crash). The browser renders the same assembly live via `renderMasterAsync` ([#194](https://github.com/enscribejs/enscribe/issues/194)): it pre-fetches each `<section src>` child against the document base URL, then runs the same assembler — a failed child fetch renders a visible inline error (always-renders)
- [x] Multi-file source, book level — a `<meta type=book>` master assembles book-part `src` children (`<chapter src>`, `<preface src>`, `<appendix src>`, …) into one `<book>` with front/body/back regions, the same way the article master assembles `<section src>` (epic [#190](https://github.com/enscribejs/enscribe/issues/190)). The assembler is document-class-agnostic — it imposes no wrapper; it passes the master's `<meta>` through and the pipeline structures the assembled tree per `<meta type>`, so an assembled multi-file book is the same tree a single-file book produces. Parts route by type (preface→front, chapters→body, appendix→back); per-chapter figure/section numbering and cross-chapter `<ref>`s resolve over the one assembled tree (chapter 2's first figure is 2.1, a chapter-2 ref to a chapter-1 figure resolves to 1.1); the assembled book exports DTD-valid BITS. Live (`renderMasterAsync`) and static (CLI `build`) render byte-identically — and the static `build` now publishes a book as **separate per-chapter pages by default** (the publishing row below; `--single-page` for the whole book in one file)
- [x] Multi-file source, website level — the **website** document type (`<meta type=website>`), the third document class: the master's `<nav>` of `<item>` pages (external `src` or inline) and `<nav-group>` groups assembles into a site, each page rendering natively as an article or a book. The static `enscribe build` emits a **dir-per-page** site by composition ([#300](https://github.com/enscribejs/enscribe/issues/300)) — each page numbers in its own native scope (a book figure stays "2.1"), every page's cross-reference registry merges into one site registry, and a cross-page `<ref>` resolves to the target's native number and links to its owning page (or book chapter-page) in all four directions (proven by `cli/test/website-xref.test.js`); a broken `<a {slug}>` degrades inline (always-renders). The live SPA renders the same site client-side via a `?page=slug` History router with the persistent site chrome (sticky top bar with `<nav-group>` dropdowns, an opt-in `<config sidebar>`, a per-page on-this-page rail); a book page renders as a native book, not page-scope-flattened ([#314](https://github.com/enscribejs/enscribe/issues/314)); #320 then **deleted** the page-scope flatten (`buildWebsiteTree`/`buildLiveWebsite`/`renderLiveWebsitePage` + the `numbering.js` `'page'`-scope branch) so both surfaces compose **one** native way, proven static≡live directly over the real build and SPA by `cli/test/website-xref.test.js` ([#320](https://github.com/enscribejs/enscribe/issues/320)); and authored `<a {slug}>` internal links resolve at render time on both surfaces off the same merged registry, with meta-slug identity ([#318](https://github.com/enscribejs/enscribe/issues/318)). Design of record: `notes/specs/website.md`. **Remaining:** inline-page rendering; and opt-in per-page section numbering (master-`<config>` threading)
- [x] Cross-file project registry & assets ([#190](https://github.com/enscribejs/enscribe/issues/190)) — across a multi-file master + its children: every `<library>` merges into one project-wide **citation registry** (a `<cite>` in any file resolves against a reference declared anywhere); **per-chapter bibliographies** (`split_bib`) list a chapter's own cited refs while a book-level `<bibliography>` lists all; the **`<endnotes>` placement marker** renders the collected end-notes at an authored position (per-chapter in a book, document-level in an article — single-page, separate-pages, and BITS); and the **`<data>` embedded-asset registry** is complete — an asset declared in `<data>` (`<fig #id png>…</fig>`) resolves at a body `<fig src="@id" />` (embedded + external, every media type png/jpg/jpeg/svg/gif/webp, cross-file merge with a last-wins collision flag), cross-referenced by `<ref @id>`, with a JATS `<graphic>` export (`data:` URI or file path, DTD-valid for JATS 1.3 + BITS 2.0; an external file asset is bundled into a portable `assets/` dir by `export-jats --package` — see the JATS interop section)
- [x] Opaque data store + consumer-agnostic `@id` ([#313](https://github.com/enscribejs/enscribe/issues/313), slices 1–2 + consumer wiring) — a `<dataset #id format=csv>…</dataset>` (long-form required — the pipe form truncates the payload at the first `>`, which datasets routinely contain) inside `<data>` stores CSV/TSV/JSON/… as **opaque bytes** under an id (never markdown-parsed; a `#`/`*` in the payload is held verbatim), harvested into the one project store beside the embedded-asset registry. A consumer pulls it by `@id` through a **neutral resolver** (`resolveAssetReference`: id → bytes + status, no media assumption) and interprets the bytes itself: `<table src="@id">` renders a stored dataset as a **grid** (store the data once, render it as a table — the first cross-consumer use); `<diagram src="@id">` feeds a dataset as an engine's **source** (a Mermaid/abc diagram — a format-hint/engine mismatch is a visible error, since the engine renders the source verbatim and enscribe cannot re-read it); `<code src="@id">` renders one as a **verbatim code listing**; and `<fig src="@id">` keeps its image interpretation (data: URI / path). The diagram/code pair share a small `readDatasetSource` helper. Every consumer's unresolved/wrong-kind `@id` is the **same visible `__asset-error`** (a `<table src="@nope">` no longer fails silently). *Remaining (#313): a `<plot src="@id">` consumer (a trivial new caller of the resolver) and a `<dataset>` JATS projection. Binary packaging is shipped for both self-contained deliverables — the single-file HTML build (see below) and JATS export (`--package`: external file assets → an `assets/` dir with href rewrite; see the JATS interop section).*
- [ ] Executable code blocks — JS / Arquero / Vega-Lite

## Rendering & output

- [x] HTML output — external CSS/fonts by default, self-contained on request (`embedResources`); **pretty-printed for readable view-source** (#117) — block elements indented onto their own lines, visual-neutral (only insignificant inter-block whitespace changes; `<pre>`/`<code>`/math interiors and inline custom elements `<inline-math>`/`<term>` are kept in the inline flow, so formatting never inserts a rendered space)
- [x] Rendered citations inlined; conditionally-injected hover previews (notes / refs / citations)
- [x] Bundled subsetted fonts (Inter, Source Code Pro) and patched KaTeX fonts
- [x] Default stylesheet with theme variables (`default.css`) — styles every shipped feature hook from one custom-property palette (border looks, section numbers, callout types, captions/labels, the show-source disclosure, cross-refs, errors)
- [x] DSL rendering modes — `skip` default, `live-link` / `live-inline`, and `static` (build-time SVG) for ABC
- [x] DSL "See source" disclosure — opt-in `<config show-source=true />` reveals the authored Mermaid/ABC source behind a rendered block in a native `<details>` control (no JavaScript); off by default, theme styles the control
- [x] Client-side rendering — browser library (`render` / `renderInto` / `executeAssets`), `enscribe.browser` bundle
- [ ] Code syntax highlighting (not yet wired in)
- [ ] Render-mode lowering — lossy lowering of custom elements to plain `<h1>`/`<h2>` (gated on a design decision)
- [x] Table-of-contents sidebar (opt-in, build-time, responsive) — for an article a single nested sidebar; for a book the left chapter rail of the three-column reading interface (below)
- [x] Config-driven contents listing ([#218](https://github.com/enscribejs/enscribe/issues/218), the ToC half of `notes/specs/toc-and-numbering.md`) — the contents listing read from the document's `<config>` in the **shared compiler**, so the static build and the live render honor it identically. For an **article** the listing *is* the contents (inline or floating sidebar). For a **book** it is honored across all three shapes ([#226](https://github.com/enscribejs/enscribe/issues/226)): the chapter rail is the book's table of contents, and `<config toc>` adds a contents **overview on the cover** — inline in the single-page build, and (built at assembly time from the chapter/section tree) on the cover of the default separate-pages build and the live render; `toc-location=left|right` on a book is a located diagnostic (the chapter rail is the sidebar). (The static≡live property is the one the docs site's live-ToC parity gap, #207, will be closed with.) Default **off**. `<config toc=true>` generates the listing from the heading tree (entries link to their headings); `toc-depth` bounds the listed levels; `toc-title` names the heading; `toc-location` places it `body` (default — inline at the top, after the title block, shown in full), `left`, or `right` (a sticky, scroll-aware sidebar whose initial expansion is `toc-expand`, deeper levels collapsible in place); `<section +unlisted>` (a new sectioning-element boolean) drops a heading and its subtree from the listing. A **render product** (Rule 2 — generated from structure + config, never written into the source); the CSS rides with the listing (injected only when one renders), so a non-ToC document is byte-identical (additive). This is the config-driven source of truth; the legacy build-passed `toc` option (the sidebar/book-interface rows above) is unchanged. **Section numbering** (`number-sections` / `number-depth` / `+unnumbered`) shipped as the sibling half; the bare-boolean authoring form (`<config toc>`, `<section unlisted>`) shipped in [#219](https://github.com/enscribejs/enscribe/issues/219); the docs/examples adoption that lights up the floating ToC is the remaining follow-on
- [x] Config-driven book navigation ([#221](https://github.com/enscribejs/enscribe/issues/221), `notes/specs/book-navigation.md`) — the book reading chrome read from the book master's `<config>` in the **shared book model** (`book-scaffold.js → resolveBookNavConfig`), so the static separate-pages build and the live render gate it identically. Book-only, **on by default for books** (declaring `<meta type=book>` opts into book conventions) except `back-to-top`: `chapter-nav` (the chapter rail), `chapter-nav-depth` (`1` = chapters, `≥2` = chapters + their sections nested), `page-navigation` (prev/next), `cover` (off = land on the first chapter — a static index redirect / live empty-route to chapter 1), `back-to-top` (a scroll-to-top control), `on-this-page` (the per-chapter "on this page" rail; off drops the reading interface to two columns — #248), `split-by` (`chapter` built; `section`/`none` deferred with a note). Defaults reproduce the pre-#221 chrome byte-identically (the conditional CSS/JS rides only when a feature is active); the toggles drive all three shapes — single-scroll, separate-pages, live (proven by `book-nav-config.test.js`). The legacy build-passed `toc` one-scroll reading interface is unchanged
- [x] ToC scroll-spy — highlights the current entry (and its ancestor trail) in the sidebar as the reader scrolls, via an injected inline `IntersectionObserver` script with `aria-current`; ships with the ToC sidebar, a pure progressive enhancement (the first first-party hand-authored render JS). For a book it is the sole left-rail highlighter (no competing paging nav), paired with a second script that drives the right "on this page" rail
- [x] Book reading interface — a book document with a ToC renders as **one continuous scrolling document** with three-column chapter-navigation chrome: a left chapter rail (front-matter unnumbered, body chapters arabic "1 · Introduction", back-matter lettered "A · Notation"; active chapter a tinted block with a left accent), static prev/next chapter links at each chapter foot, and a right "on this page" rail of the current chapter's sections (scroll-spied). Book-gated — article ToC behavior is unchanged; all chrome markup is static (byte-identical static≡live), the highlighting/visibility a post-render enhancement. A single-chapter-at-a-time **paging** view remains available opt-in (`chapterNav: true`). This is the **one-file** projection; the static `enscribe build` also publishes the same chrome as **separate per-chapter pages** (next row)
- [x] Static separate-pages book build (publishing track, P1) — `enscribe build` emits a book as **one standalone HTML page per chapter** at deterministic per-chapter URLs (`1-counting-elephants.html`, `a-field-data-sheets.html`, …) plus an `index.html`, the shareable published artifact (open a `chapter-N.html` link with no JS). Each page carries the reading-interface chrome (the chapter rail linking to every chapter's page, prev/next to the adjacent pages, the current chapter's on-this-page rail, and a return-to-cover masthead — the book title — linking back to `index.html` so the cover is reachable from every page) and that chapter's content (the per-chapter render). **Cross-chapter references link across pages** — a ref to a figure in another chapter resolves to that chapter's page + anchor (`1-counting-elephants.html#fig:transect`); in-chapter refs stay in-page anchors. Default for books; `--single-page` builds the whole book in one file (also the reference render the per-chapter content is proven byte-identical to). The live routed lazy render is the editing-surface track's read-only foundation — see the next row
- [x] Live app-shell book render (editing-surface track, L2, read-only) — a single app-shell `index.html` renders a book **live in the browser from its `.emd` source**: it fetches the master + its chapter children, runs the cheap global pass once (numbering + cross-reference resolution), then renders the **current** view via the same per-chapter projection the static build publishes, mounted with the reading-interface chrome and routed by the **chapter-as-page scheme** — a chapter is an addressable page on the query (`?chapter=<stem>`, or `?page=<slug>&chapter=<stem>` inside a website; the live analog of the static per-chapter `<stem>.html` file) and the URL **hash is purely a section anchor within a chapter** (`?chapter=<stem>#<id>`), so a section is independently deep-linkable (chapter and section no longer compete for one slot) — rendering each view lazily on navigate and caching the rendered ones. Opening it (no `chapter`) lands on the **cover** (book-title hero + lede, the live counterpart of the static `index.html`), and every view carries a **return-to-cover masthead** (the book title → the cover route), so a chapter round-trips to the cover exactly as a static chapter page round-trips to `index.html`. Cross-chapter references resolve live by rewriting to the owning chapter's route (`?chapter=<owner>#<anchor>`, the live analog of the static `<owner>.html#anchor` rewrite) — a SAME-chapter ref stays a bare `#anchor` (a pure in-page scroll). The live per-chapter content is byte-identical to the static page's content, and the live cover body is byte-identical to the static cover body (the published≡live parity, proven). Browser entry `mountLiveBook` / `mountLiveBookFromUrl`; served over HTTP (the shell `fetch`es). The **read** view is the foundation; the **edit loop** that builds on it shipped — see the next row. (`enscribe serve` is a later convenience; the shells are dev-preview fixtures for now.)
- [x] Live book edit loop (editing-surface track — the [#203](https://github.com/enscribejs/enscribe/issues/203) payoff; preview-only) — the live app-shell render gains an **authoring loop**: on a chapter view, a **CodeMirror 6** pane (a GitHub-style Write/Preview tabbed pane) shows that chapter's `.emd` source, and a debounced edit re-renders **only that chapter** live — never the whole book. Incremental by construction: only the edited chapter is re-**parsed** (a memoized parse; unchanged children clone from cache), the cheap global pass re-runs over the whole assembled tree (so a structural edit — a new labeled figure — renumbers cross-references everywhere, and a reference in another chapter shows the new number on navigate), and only the current chapter is re-**rendered**. The engine owns the loop (in-memory source map, debounce, rebuild, preview re-render, the tabs, the "preview — unsaved" marker) and exposes an editor-**adapter** seam (`editor.mount(el, {value, onChange})`); the shell loads CodeMirror from a CDN and provides the adapter, keeping it out of the engine bundle. Editing is a **document-level capability** (the settled model): editability is governed by `<config editable>` (default **on**) — a document declares whether it offers the editor, and the engine gates editing *down* from that (the host always provides the editor adapter, so `<config editable=false>` makes the engine *decline* to build it; the document never needs to *load* CodeMirror itself). Display defaults to **preview** — the rendered document, the Source editor one click away (shipped). And book pages edit **per-chapter in the website SPA**, not just the standalone shell (shipped). *Remaining piece:* the `<config editable>` kwarg is not yet registered, so for now editability is still flipped by the host (the interim mechanism) — `mountLiveShell`'s explicit `edit` flag, else a `data-enscribe-edit` attribute on the mount element, else `?edit` at runtime; off → read mode (no editor, no CodeMirror load), on → the loop. The shell **plumbing** — the masthead + edit-mode chrome CSS (`enscribe-shell.css`) and the default CodeMirror editor adapter — ships in the package (the `src/shell/` shell layer, alongside the editor-agnostic core engine), so a shell **references** it rather than hand-copying it (#214). The shell is **generated**, not hand-written — `emitLiveShell({ master, title, edit, assetBase })` (pure) emits the minimal shell, and **`enscribe build --live <master> -o <dir>`** writes a portable, self-standing **live folder** (the emitted shell + the master/children + the engine bundle + shell assets copied in, referenced relatively — no CDN for the chrome) (#215). The live render handles **both a book and a single-document article** (#216): the emitted shell is type-agnostic — at runtime `mountLiveShell` fetches the master, reads `<meta type>`, and dispatches a book to the book path (unchanged) or an article to a small **article path** (`mountLiveArticle`). An article is the **simple case** — one unit, so no cover, no chapter rail, no hash routing, no per-chapter cache: read mode renders the one document; edit mode is the same Write/Preview loop collapsed to the single source (editing the master re-renders the whole article, and the single global pass keeps in-document cross-references correct). The two paths **share** the genuinely common helpers (engine load + assemble, the editor adapter, the Write/Preview UI); the book path is unchanged. **Preview-only** — edits live in memory and are lost on reload; write-back (save) is the named follow-on. Math re-renders live (build-time KaTeX); DSL diagram re-activation is deferred. Read mode (the switch off) is byte-identical to the read row above
- [x] Single-file self-contained document (delivery track — `notes/specs/delivery-modes.md` §Single-file; [#329](https://github.com/enscribejs/enscribe/issues/329)) — **`enscribe build --single-file <doc.emd>`** emits ONE self-contained `.html` that carries the document's source EMBEDDED in an inert `<template>` (HTML-escaped, round-trips via `.content.textContent`). At mount the engine reads that embedded source via **`mountLiveDocument`** — the read-from-provided-source entry that runs the same `<meta type>` dispatch + `?edit` switch as the served `mountLiveShell`, only WITHOUT fetching the document (the source-provider seam: `mountLiveShell` fetches then delegates here; the single-file shell reads its `<template>` and calls here; `loadAndAssembleMaster`'s child loader is injectable too, default fetch). **Editable iff self-contained** (no `<… src>` children — the existing `childSrcs.length === 0` test): a self-contained doc wires the editor + honors `?edit`; a master with children (or a website) is emitted **render-only** with a warning. Chrome + display assets load from the **web** (jsDelivr default — `raw.githubusercontent.com` serves `text/plain`+`nosniff` and won't execute), so the file is small (shell + content, no engine inlined). The served Live/static modes are unchanged (additive; `mountLiveShell` refactored to delegate, output-neutral). The file also **carries its referenced assets** ([#313](https://github.com/enscribejs/enscribe/issues/313) slice 4, binary packaging): embedded `<fig #id fmt>base64</fig>` / `<dataset>`s already travel in the source, and EXTERNAL references are embedded at build (`embedExternalAssets`) — an external `<fig src="local.png">` becomes a `data:` URI, an external `<table … src="local.csv"/>` becomes inline data — so the one file renders its figures and data tables when opened **from anywhere**, no dangling path (an `@id`/`data:`/http(s) src is left untouched; embedding an asset never changes editability). **Still unbuilt:** site-in-a-file (embedding a multi-document master's STRUCTURE children — book chapters / website pages) and inlined-offline chrome assets (`file://` with no network)

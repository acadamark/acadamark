# `<note-list>`

A container for collected notes. Used to gather end-notes, chapter-notes, or other note collections at a designated location in the rendered output.

## Semantic intent

`<note-list>` is the structural container that gathers `<note>` elements when the document's note-position setting calls for collection. End-notes go into a `<note-list>` at the back-matter location. Chapter-notes go into a `<note-list>` at the end of each chapter.

This element is normally **not authored directly**. The `acadamarkNotePlacement` plugin generates `<note-list>` elements based on the document-level `note-position` setting, collecting notes from throughout the document into the appropriate position.

## Why it exists

Even though authors don't typically write `<note-list>`, the element is a real structural part of Layer 1 because:

- It needs to appear in the rendered HTML (browsers and JATS export need a container for the collected notes).
- It needs to be the cross-reference target for note references that resolve to "see end-notes" or similar.
- It can be authored explicitly when an author wants a specific layout that the placement plugin doesn't support.

## When authors might write it explicitly

A few cases where explicit `<note-list>` makes sense:

**Custom placement.** The document has `note-position=end` but the author wants the end-notes to appear in a specific location not at the document end. They write `<note-list>` at that location, and the placement plugin honors the explicit container rather than generating one elsewhere.

**Multiple note collections.** A document has both end-notes for the article body and a separate set of chapter notes. The author writes two `<note-list>` elements with different ids (or different `type` values) and the placement plugin distributes notes accordingly.

**Manual notes management.** For some specialized publishing workflows, the author wants explicit control over what notes appear and where. They write `<note-list>` with explicit `<note>` children rather than relying on collection.

These are unusual. The default workflow is: write `<note>` inline in your source; set `note-position` at document level; let the placement plugin generate the `<note-list>` automatically.

## Content

A `<note-list>` contains zero or more `<note>` elements. The notes inside have already been numbered by the time they appear here (the numbering plugin runs before the placement plugin).

## Attributes

`type` indicates the kind of note collection:

- `end-notes` — collected end-notes for an entire document.
- `chapter-notes` — collected notes for one chapter.
- `footnotes-collected` — page footnotes pulled into a single block (rare; some print layouts).
- `other` — anything not covered above.

This classification lets CSS and JATS export distinguish between different note collections within the same document.

## JATS mapping

| acadamark | JATS |
|-----------|------|
| `<note-list>` | `<fn-group>` |
| `<note>` (inside `<note-list>`) | `<fn>` (inside `<fn-group>`) |
| `type` kwarg | `content-type` attribute on `<fn-group>` |

The mapping is direct. JATS's `<fn-group>` is the natural counterpart for collected notes.

## Authoring patterns

**Default workflow (no explicit note-list).**

```
<article note-position=end | My Paper>
<meta>
  <author | Jane Goodall>
</meta>

<section | Introduction>
The argument is straightforward<note | But not without nuance.>.

Other content<note | Another note.>.
```

The placement plugin generates a `<note-list>` at the end of `<article-back>` containing both notes.

**Explicit note-list with custom position.**

```
<article note-position=end | My Paper>

<section | Body>
Content<note | A note.>.

<section | Acknowledgments>
Thanks to colleagues.

<note-list type=end-notes>
<!-- The placement plugin populates this with collected notes. -->
</note-list>

<bibliography source="refs.bib">
```

The author writes an empty `<note-list>` to mark where end-notes should appear (between Acknowledgments and Bibliography). The placement plugin populates it.

**Multiple note collections.**

```
<book | The Book>

<chapter | First Chapter>
Content<note | Chapter one note.>.

<chapter | Second Chapter>
Content<note | Chapter two note.>.

<note-list #author-notes type=end-notes>
</note-list>

<note-list #editor-notes type=editor-notes>
</note-list>
```

Two collections appear at the back of the book, distinguished by id. The author would also need to mark which notes go in which collection (probably via a kwarg on `<note>` itself, though that's a future feature).

## Render-mode lowering

`<note-list>` is a custom element. In render mode, it lowers to `<aside class="note-list">` or `<section class="note-list">`, depending on what semantic role makes the most sense in the surrounding document.

The `<note>` children inside lower according to their own render-mode rules, typically becoming `<li>` elements within an implicit list, with the note number as a leading marker.
